# LLM 音色设计：按官方「音色描述编写」规范重写

实现位置：`assets/js/tts-service.js`（`VOICE_DESIGN_RULES`、`DELIVERY_RULES`、`VOICE_PLAN_SCHEMA`、`composeVoiceInstruction`、`synthesizeSegment`）。
验证：`node tests/tts-voice-design.test.mjs`。
规范来源：MiMo 官方 SKILL `mimo-v2-5-tts` 的「音色描述编写」与「自然语言控制」两节。

## 一句话结论

官方把 `voiceDesign` 定义为**嗓子的身份卡**：只写这副声音本身长什么样，不写场景、不写动作、不写这段要说什么。旧 prompt 把它当成"对本段内容的音色建议"来写，于是同一个角色在不同段落被赋予了不同的嗓子。

## 官方规范与旧实现的差距

| 官方 SKILL 要求 | 旧实现 | 后果 |
| --- | --- | --- |
| 一到两句话 | `长度 1-4 句` | 描述越长，两次调用之间的自由发挥空间越大，同一角色跨段音色漂移越明显 |
| 不写场景 | `可补充……场景感` | 直接违反硬约束；写进"身份卡"的场景与其它段落的情节互相矛盾 |
| 必写：身份锚点（年龄段 + 性别，决定基频） | 只说"性别与年龄感" | 没点明这是地基，模型常把年龄混在形容词里一笔带过 |
| 必写：声音质感 = 气息走向 + 共鸣位置 + 吐字 + 音色底色，用可感的动词或比喻 | 只说"音色质感" | 模型退化成"声音很好听""有磁性"这类零信息形容词 |
| 可选项：风格/身份锚点（播音员风格、法庭陈词风格…） | 无 | 丢掉了官方"强烈推荐"里最省 token 的辨识度来源 |
| 可选项：辨识度小癖好（字尾颤音、胸腔闷笑…） | 无 | 同一角色的多段音频听感趋同，无人格记忆点 |
| 不写"这次要说什么" | 旧规则把 `delivery` 与 `voiceDesign` 混在同一句要求里 | 演绎指令被写成音色词，污染身份卡 |

另外旧版没有给任何正例。纯规则描述对模型的约束力远低于规则 + few-shot：现在给了 4 条正例，密度与实际输出对齐（每条 1-2 句、开头必须是"年龄段 + 性别"、结尾带一个风格锚点或癖好）。

## 新的规则结构

`VOICE_DESIGN_RULES` 分四段：

1. **定位**：`voiceDesign` 会原样作为 `mimo-v2.5-tts-voicedesign` 的 `context` 输入，是该说话人唯一的音色来源。
2. **必写四项**：身份锚点 → 声音质感 → 语速节奏 → 情绪底色。顺序即权重，身份锚点必须放最前。
3. **强烈推荐两项**：风格/身份锚点、辨识度小癖好。
4. **硬约束**：1-2 句白描、不分段不列条、禁场景/动作/台词复述、禁后期工程词、禁真实演员与 IP 名、方言仅在明确需要时、不同角色至少在「性别 / 年龄段 / 共鸣位置」里拉开两项、同一说话人跨段**逐字相同**。

正例（写进 prompt，测试逐条校验）：

```
- 中年男性，声线低沉醇厚、胸腔共鸣重，吐字慢而字字顿挫，情绪克制。法庭陈词风格，句尾习惯性下沉。
- 青年女性，气息偏浅、贴在鼻腔上方，语速快而连贯带明显气口，情绪松软微甜。偶尔把尾音拖长半拍。
- 青年男性，声音清亮偏薄，咬字干脆、唇齿音很轻，语速忽快忽慢。电竞解说风格，兴奋时尾音上扬发尖。
- 老年男性，嗓子里带砂纸般的颗粒感，气息短、句间停顿长，情绪温和。评书先生风格，说到起劲处会先吸一口气。
```

## 把 delivery 从音色里剥出来

`mimo-v2.5-tts-voicedesign` 只有 `context` 一个通道（官方原文：*"mimo-v2.5-tts-voicedesign 则通过这个选项同时控制音色和风格"*）。所以"音色"和"这一段怎么演"必须挤进同一段描述里，而每段又是**独立请求**——只要演绎提示里出现音色词，这个说话人在本段就会换一副嗓子。

新增 `DELIVERY_RULES`：

- 允许五类：语速、气息（换气/屏息/气息发虚）、停顿、重音、情绪起伏。
- 禁止项直接列举音色词：年龄、性别、嗓音粗细、沙哑、清亮、共鸣位置、音域、口音、方言。
- 平淡段落**留空**。留空是本设计里最有效的一招：`instruction` 与其它段逐字相同，模型的输入完全一致，音色最稳。

拼装集中到一个纯函数：

```js
const VOICE_DELIVERY_PREFIX = '本段演绎（只调整这一次的语速、气息、停顿、重音与情绪起伏，不改这副嗓子的音色底色）：';

composeVoiceInstruction(voiceDesign, delivery)
// delivery 为空  →  voiceDesign                      （逐字相同，可跨段复用）
// delivery 非空  →  `${voiceDesign}\n${PREFIX}${delivery}`
```

改之前是 `` `${voiceDesign} 本段演绎要求：${delivery}` ``——用空格连接，模型容易读成一整句音色描述。现在换行 + 显式前缀，并在前缀里写明"不改音色底色"，把边界说在拼装处而不是只写在 prompt 里。

## 端到端不变量

| 不变量 | 证据 |
| --- | --- |
| 合成的 `instruction` 恒等于 `composeVoiceInstruction(身份卡, delivery)` | 测试逐段比对请求体 `messages[0].content` |
| 有 delivery 时，第一行仍是**原样**身份卡 | 测试取 `split('\n')[0]` 与卡全文比较 |
| 无 delivery 时，`instruction` 与身份卡**逐字相同**（不多一个字符） | 同上，全等断言 |
| 同一角色所有段的第一行只有 1 种取值 | 测试用 `Set` 去重后 `size === 1` |
| voicedesign 请求不带 `audio.voice` | 官方：音色完全来自 `context` |
| voicedesign 正文不加 `(风格)` 标签 | 官方明确 voicedesign 暂不支持音频标签，加了会被念出来 |

最后一条是真实风险点：`applyStyleTag` 原本只挂在 preset 链路（`synthesizePresetChunk`），voicedesign 走 `segment.text` 原样。测试把它锁成回归契约，避免以后"顺手统一"把标签塞进 voicedesign 正文。

## 两份官方材料的口径差异（取舍说明）

MiMo 自己有两份材料，在这一节上是**冲突**的，必须明确站哪一边，否则以后有人会拿官网文档来"修正" prompt：

| 条目 | 官网文档站「使用指南」 | MiMo-Skills `SKILL.md` | 本实现采用 |
| --- | --- | --- | --- |
| 长度 | 「1-4 句即可」 | 「一到两句话」 | SKILL（1-2 句） |
| 场景描写 | 列为**可选加分维度** | **硬约束：不写场景** | SKILL（禁剧情场景） |
| 年代参照 | 列为可选加分维度 | 未提及 | 折进「风格/身份锚点」 |

取舍理由：

1. **语料场景不同。** 官网文档面向 Studio 的「一次性设计一段音频」，没有跨段复用压力；RP-Hub 是**逐段独立请求**——同一角色有 N 段就有 N 次独立生成，描述越长越松，N 段就越像 N 个人。SKILL.md 的立论正落在这上面：*写得越凝练，越容易跨场景复用*。
2. **SKILL.md 更新、更面向执行。** 它是 version 0.1.2 的 agent 实操规范，而官网文档是产品页文案。
3. **场景信息不能真丢。** 官网文档里 `narrating a nature documentary`、「在给投资人路演」这类示例，本质是**体裁锚点**而不是剧情场景——它告诉模型"这副嗓子属于哪种节目"。本实现把这类信息全部收进官方的第 5 项「风格/身份锚点」（播音员风格、法庭陈词风格、电竞解说风格、评书先生风格）：既保住语境信息，又不写"她此刻走在雨里"这种一旦被跨段复用就自相矛盾的剧情场景。

因此 `VOICE_DESIGN_RULES` 禁的是**剧情场景**（「在发布会上」「值夜班时」「祠堂的阴影里」），不是体裁语境。测试里被断言必须清除的「场景感」一词，指的是旧版规则 `可补充……场景感` 把剧情场景写进身份卡的措辞。

## 缓存签名必须带上 prompt 版本

prompt 是"音色的生成输入"之一，和模型名、音色 ID 同级。旧实现的 voicedesign 缓存签名是：

```
[ttsApiUrl, ttsModel, ttsDesignModel, ttsDesignApiUrl, ttsContextRange, ttsCustomInstruction].join('|')
```

不含 prompt。后果是**改了规则却听不到变化**：设置没动 → 缓存键没变 → `audioCache`/`segmentCache` 继续命中旧音频，用户以为 prompt 白改了。

现在签名末尾追加 `VOICE_DESIGN_PROMPT_VERSION`（当前 `card-v2`）。规矩：**改 `VOICE_DESIGN_RULES` / `DELIVERY_RULES` / `VOICE_PLAN_SCHEMA` 的任何一句，都要递增这个版本号**，测试里锁了格式 `card-vN` 与下限 `>= 2`，但"是否真的递增了"仍需人工核对——这条记在这里，不靠测试。

## 两个刻意不做的动作

**不启用 `audio.optimize_text_preview`。** 官方文档给了这个参数（仅 `mimo-v2.5-tts-voicedesign` 支持，开启后会对目标文本智能润色、甚至自动生成播报文本），它能省掉 `assistant` 消息。但本项目的前提是"只切不改"——`SEGMENT_RULES` 明令 `segments[].text` 必须能在原文里找到对应内容。开了它等于让服务端二次改写正文，剧情会被悄悄润色掉。请求体里永远不传这个字段。

**不在一次朗读里重摇同一段。** 官方提示 TTS 有随机性，同样的输入效果可能不同，需要时"多生成几次以供挑选"。段级缓存与这条天然冲突：同一段文本第二次请求会命中 `segmentCache`，摇不出第二个版本。这是刻意的——RP-Hub 的一次朗读是"整条气泡连续播放"，中途换音色比音色略不理想更糟。想重摇就走设置页的「清空朗读缓存」（`clearTtsCache`），清完再点朗读即可重新生成。

## 已知上限

官方给出的根治方案是「设计 → 克隆」：先用 `voicedesign` 生成满意的一段音频，再把该音频作为 `mimo-v2.5-tts-voiceclone` 的 `voice-file` 复用到其它文本，音色才真正锁定。本实现没有采用，原因是：

- 浏览器端每次朗读都要多一次"设计音频 → base64 上传 → 克隆合成"往返，首字延迟和额度都翻倍；
- 克隆样本需要跨会话持久化（`File`/Blob 存 IndexedDB），与当前"纯内存缓存、刷新即清"的模型不符。

当前用「逐字相同的身份卡 + 表演层隔离 + 平淡段落留空」把漂移压到工程可接受范围；真要影视级一致性，再上克隆链路。
